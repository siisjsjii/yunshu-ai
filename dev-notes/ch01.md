### ④ 翻车与返工

**1. WebFetch 被网络策略拦截**

查 FastAPI SSE 的引入版本时,`WebFetch https://fastapi.tiangolo.com/release-notes/` 返回:

> Unable to verify if domain fastapi.tiangolo.com is safe to fetch.

**绕法**:`pip download fastapi==0.141.1 --no-deps --no-binary :all:` 拉 sdist,直接 `tar -tzf` 确认 `fastapi/sse.py` 与 `tests/test_sse.py` 存在,再 `cat` 源码读接口签名。比查 release notes 更硬 —— 拿到的是实际发布的代码。

**2. 差点凭记忆手拼 SSE(本次最大的一次未遂返工)**

我原本的设计是 `StreamingResponse` + 手写 `f"data: {json}\n\n"`。Context7 查出来 FastAPI 0.141.1 已有原生 `fastapi.sse.EventSourceResponse` / `ServerSentEvent`,读源码后确认它会自动处理 JSON 序列化和换行符转义。

如果按记忆写,会在"token 里含换行符导致 SSE 帧结构被破坏"这个坑上栽跟头 —— 而且这种 bug 只在模型输出多行文本时才复现,极难定位。

**3. LangChain 1.x 的 Responses API 陷阱**

Context7 的官方文档明确警告(原文):

> The OpenAI provider defaults to the Responses API, which most OpenAI-compatible gateways do not implement. If your provider only supports the Chat Completions API, invocation will likely fail. Disable the Responses API explicitly.

`ChatOpenAI` 不传 `use_responses_api=False` 就会走 Responses API,DeepSeek 不支持。这是"第一条 curl 就失败"级别的问题,已写成 spec 第 2.1 节的硬约束 + 单测守护项。

**4. 用户回答歧义,停下来问清楚了**

我问的是"抽取不做自动重试",用户回"抽取可以不做测试"。这两个意思差很远 —— 如果理解成"不用给抽取写测试",就直接违反用户自己开头提的"纯 Prompt 用评估集验证"。停下来确认后:是"不重试",**评估集照做**。

教训:一句话里同时出现"测试"和"重试"这种形近词时,不要挑一个顺眼的解释往前走。
