### ④ 翻车与返工

**自审抓到一个真 bug**(计划阶段就修掉了,没带到实现):

`SessionStore._enforce_capacity` 原本写成"从最老开始淘汰,遇到被持锁的跳过、继续看下一个"。看着合理,实际语义是反的 —— 当最老的会话正在流式时,它会越过该会话去删**更新的**会话。

正确做法:遇到被持锁的**整个停下**,宁可短暂超出 `max_sessions`。已修,并补了能抓住它的断言:

```python
assert store.history("s2") == [_msg("二")]
```

这个 bug 的教训是:**"跳过"和"停下"在处理有序淘汰时不是一回事**。跳过会打破顺序不变式。

同时清掉三处自己的手滑:

1. 在测试里**故意埋了一个语法错误**,想用来验证"先跑测试"这一步没被跳过 —— 馊主意,只会让执行者困惑,已删。
2. `dict[str, asyncio_Lock]` 占位符 —— 直接写成正确代码即可,不该留"实现时记得改"。

### Task 3 · token 预算与裁剪

**① 用户关键原话**:本阶段用户无发言。

**② 关键产出**:提交 `89a46d7` → 修复 `5582b91`。`app/memory/trim.py` + 12 测试。**走了 1 轮修复**。

**③ 被拒绝 / 被纠偏**:审查者提了一条 Important,并标注"plan-mandated"(计划自带的)。按流程我必须先裁决再动,不能因为"计划就这么写的"就驳回。**裁决:接受,进修复循环** —— 计划不是"要求缺这些测试",而是遗漏了它自己规定的语义的测试;补测试是强化合规,不构成与计划冲突。

**④ 翻车与返工**:

**这是本章第一次真正吃到 subagent 审查的红利。** 我在计划里写了五条"设计语义",其中两条**完全没有任何测试守护**:

- **语义 #4**:`select_history` 遇到放不下的轮要 `break`(整个停下),不是 `continue`(跳过它去找更老的)
- **语义 #5**:`_to_rounds` 要把"尾部孤立的 user 消息"当成独立一轮

问题在于我写的测试**看起来覆盖了这两条**:

```python
def test_select_history_never_returns_half_a_round():
    history = [_u("很长很长的问题"*10), _a("很长很长的回答"*10), _u("新问题"), _a("新回答")]
    kept = select_history(history, available_tokens=1)
    assert kept == []
```

`available_tokens=1` 时**两轮都放不下**,所以 `break` 和 `continue` 的结果都是 `[]` —— 这个测试根本区分不了两种实现。而所有测试历史都是偶数长度,`_to_rounds` 里那个 `if pending:` 尾部分支**从未被执行过一次**。

也就是说:把 `break` 改成 `continue`,12 个测试会**全绿通过**。这两条是我自己写进 spec 的"有意设计",却零回归保护。

修复后新增的两个测试,重审者逐条算了 token 开销确认它们**在错误实现下会失败**:

| 测试 | 正确实现 | 错误实现 | 能区分? |
|---|---|---|---|
| break-vs-continue | `[]` | `[小问题,小回答]` | ✅ 超长轮 ≈400 tokens vs 预算 ≈6,不靠边界巧合 |
| 尾部孤立 user | `[被打断的问题]` | `[]` | ✅ |

**教训**:测试通过 ≠ 语义被守护。断言必须能区分正确与错误实现 —— 如果两种实现下断言结果相同,这个测试只是在"执行代码路径",没有在"钉住行为"。这跟我前面 Task 1 那个"`.env` 让测试假绿"是同一类问题的两种形态。

### Task 4 · 会话存储(TTL + LRU + 每会话锁)

**① 用户关键原话**:本阶段用户无发言。

**② 关键产出**:提交 `026c306` → 修复 `d47ba45`。`app/memory/store.py` + 17 测试,全量 41 passed。**走了 1 轮修复**,且以我**修改 spec** 收尾。

**③ 被拒绝 / 被纠偏**:**实现者驳回了我修复指令的一部分,而且它是对的。**

审查者报了一条 Minor:`lock_for` 对"从未被 append 过的 session_id"会留下永不清扫的 `_locks`/`_touched` 孤儿条目。我判定审查者定级偏低,提级为 Important 并派了修复,指令是"清扫所有非持有中的孤儿条目"。

实现者指出:**这会让 `lock_for("s1")` 连调两次时,第二次在返回前就把第一次刚建的锁扫掉**,`test_lock_for_returns_same_lock_for_same_session` 会直接挂 —— 锁的幂等性被我这条指令破坏。它改成只清扫"年龄 > TTL"的孤儿。

我让重审者独立核实这个驳回。重审者把两次 `lock_for("s1")` 完整推演了一遍,结论是**实现者正确**。

**④ 翻车与返工**:

**1. 我的 spec 里有一句假命题,是审查者查出来的。**

spec 第 5.3 节写着「LRU 上限已给出内存硬上界」。审查者指出:`_purge` 只遍历 `_sessions`,`_locks`/`_touched` **完全不受 `max_sessions` 约束**,这句话是假的。

触发路径很具体:端点先 `lock_for` 再 `prepare_turn`,后者对超长输入抛 `ContextOverflowError` 返回 400 —— 那条路径下 session 永不进历史表,孤儿条目就留下了。而 session_id 客户端可控。

**2. 修复没有让这句话变真,只是让它不那么假。**

修复把"随运行时间无界增长"改成了"约 到达速率 × TTL 有界"。是真上界,但不是常数上界。

我面临一个选择:**再加一层数量上限**(约 3 行),还是**改 spec 措辞**?

我选了改措辞。理由:端点在本章**根本没有认证**,内存耗尽只是诸多 DoS 向量之一 —— 为一个无认证端点给锁对象再建第二套淘汰策略,是过度工程。已在 spec 里把上界的确切构成写成一张表,并注明"若 ch02 引入认证,应同时给这两个 dict 加数量上限"。

**这里值得记的是:我不确定自己判断对了。** 支持"加数量上限"的理由也很硬 —— 成本只有 3 行,而且"会话有上限、锁没上限"这种不对称正是以后会咬人的那类设计。如果你觉得该加,现在说比 ch02 说便宜。

**3. 修复引入一条新的 Minor**:新清扫使 `_purge` 变 O(#孤儿),`lock_for` 每次调用都付这个成本,同一 TTL 窗口内 n 个不同 id 时总工作量 O(n²)。有界,不影响正确性,已记为延后项。

**1. 我的验收脚本原样跑是「通过 0 项,失败 7 项」—— 两个真实缺陷。**

**缺陷 A(平台):中文请求体不能放 argv。** Windows/MSYS2 会在原生 curl 拿到参数前把 UTF-8 重编码成 CP936,`你好` 变成 4 个 GBK 字节,服务端全部以 `error parsing the body` 拒绝。`LC_ALL=C.UTF-8` 修不好。改走 stdin heredoc 后字节精确。

我写的是 `grep -q "20240915"` 直接打在原始 SSE 输出上。但订单号是**逐 token** 推送的,会被切成 `"202"`/`"409"`/`"15"` 三个独立帧 —— **原始字节里不存在这个连续子串**。也就是说:**即使模型完全接住了上下文,这条验收也必然报失败。**

**三方各纠正了一次,每一次都让结论更准。** 这就是为什么值得让审查者和实现者相互独立。

### 这条流程真正买到的东西

**1. 假绿测试是本项目的头号风险,而不是错误代码。**
