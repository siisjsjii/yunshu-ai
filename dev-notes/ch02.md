### ④ 翻车与返工

**1. 我判过一次「仓库里没有前端」,被时序打脸 —— 但那次判断在当时是准确的。**

我扫描时 `find` 确实没找到任何前端文件。用户随后(00:41)把原型图放进了 `asserts/`。所以这不是我漏看,而是**我的扫描与用户的动作之间有窗口**。

值得记的是我的处理:我没有因为「用户说有」就默认它存在并跳过,而是**把出处摆出来请用户澄清**。如果我当时直接假设「用户记错了,前端不在范围」,或者反过来假设「用户说有就是有,我去猜它长什么样」,两种都会跑偏。

教训:**当事实与用户陈述冲突时,先摆证据再问,不要替用户裁决**。

**2. 差点把整个章节判成「不可行」。**

ch01 留痕里有一条实测:`function_calling` → 400 `Thinking mode does not support this tool_choice`。而 `with_structured_output(method="function_calling")` 内部正是 **bind_tools + 强制 tool_choice**。

如果我把这条读成「本端点不支持 tool calling」,本章在第一步就会被判死,然后我会去问用户换模型 —— 而实际上**不需要换任何东西**。真机一探就清楚了:挂的是**强制 tool_choice**(thinking 模式不支持),**不强制则 tool calling 完全正常**。

这条是本章最有价值的一次探测。它同时说明:ch01 留痕里那条记录是**准确的但容易被误读**的 —— 错误信息里出现了 `tool_choice`,但当时没有记下"那只是强制模式特有"这一层。

**3. 差点把「只做单轮」建在模型的自觉上。**

我最初的直觉是:第二轮**仍然绑 tools**,指望模型拿到工具结果后就收敛。实测(第 4 条)确实**没再调** —— 如果我只跑这一次就下结论,会得出「模型不会再调」,然后把它写成设计。

但那是**模型行为,不是结构保证**。模型完全可以在第二轮再调一次,那就成了 Agent Loop,直接违背用户「只做单轮」的要求,而且是**偶发**违背。

改成**第二轮不绑 tools** 后,模型在结构上就没有能力再调 —— 「单轮」从「求模型自觉」变成了「代码保证」。

这跟前几次是同一类:**别把「这次观察到的行为」当成「系统的不变量」**。

**4. spec self-review 抓到 4 处会产生两种解读的歧义**(我自己写的):

| # | 歧义 | 修法 |
|---|---|---|
| 1 | `tool_result.summary` 是什么、多长 | 定义为「前端展示用摘要,截断 200 字符」,完整结果只回灌模型 |
| 2 | 会话已存在时传入新的 `user_id` 怎么办 | 明确**忽略**,以创建时为准(否则任何客户端能改会话归属) |
| 3 | `TOOL_RETRY_ATTEMPTS=1` 是 1 次总计还是 1 次额外重试 | 明确为「不含首次」,`0` 表示不重试 |
| 4 | 验收 1 的「浏览器看到徽章」脚本能不能验 | 明确脚本只验到 SSE 帧,**徽章渲染属人工确认** |

第 2 条的修法是安全相关的 —— 原文档留了口子,意味着无认证端点上任何人都能改一条会话的归属。

### ④ 翻车与返工

**1. 我的 spec 把数据库环境写臆断了 —— 而且是"连不上"级别的那种错。**

spec §7.4 原文是「`docker-compose.yml` 起 MySQL 8.4,端口 3306」。实际是 **MySQL 8.0.46**、主机端口 **3307**。两处都不对。

如果这两条错带进实现,表现会是:应用连 3306 报连接被拒,然后我去查"MySQL 没起"——而它好好地跑在 3307 上。

**根因**:我在写 spec 时,docker daemon 还没起、容器还没建,于是我**用了一个通用的默认值(8.4 / 3306)并把它写成了确定语气**。这在文档里和"实测"长得一模一样,但一个是猜的。这正是 ch01 反复强调的那类问题 —— **猜的东西必须标注为猜的**,哪怕它看起来很像常识。

已按实际回写,并在 §7.4 用「实现订正」小节显式标出原文错在哪。

**2. 顺手抓到一个真实缺口:`.env.example` 里没有 `DATABASE_URL`。**

用户的 `.env`(不跟踪)里有,但入库的模板里没有。后果是:**新克隆这个仓库的人不知道要配它**。已列入计划。

**3. 一个我差点忽略的细节:`get_settings()` 读不到 `DATABASE_URL`。**

第一次探测时我用了 `get_settings()`,得到"没有这个字段"。原因是 `Settings` 类还没实现该字段,而它的 `model_config` 设了 `extra="ignore"` —— **未知环境变量被静默丢弃**。

这不是 bug(字段本就还没实现),但它提醒了一件事:`extra="ignore"` 意味着**配置项名字打错时不会有任何报错**,只会静默用默认值。ch01 把 `OPENAI_MODEL` 设为必填正是为了对抗这类静默。本章的 `DATABASE_URL` 同理设为必填。

### ④ 翻车与返工

**1. 装完依赖连不上库 —— spec 漏了一个必需包。**

`pip install sqlalchemy asyncmy` 之后建连接,直接抛:

> `RuntimeError: 'cryptography' package is required for sha256_password or caching_sha2_password auth methods`

MySQL 8.0 默认认证插件是 `caching_sha2_password`,asyncmy 走该认证需要 `cryptography`。**我写 spec 时列了 sqlalchemy 和 asyncmy,完全没想到它。**

这正是 ch01 反复强调的那类"第一条就失败"的坑 —— 而它**只有在真连一次库里才会暴露**。已补进 spec §2 与 plan 的 Global Constraints,并标注"不是可选项"。

**2. spec 里一个我"想当然"的设计被真机推翻。**

spec §6.5(b) 原写:「`create_ticket` 的 `conversation_id` 用 `InjectedToolArg` 注入,不进模型的参数 schema」。实测发现该机制在本版本上**不完整**:

| 实测项 | 结果 |
|---|---|
| `args_schema`(原始) | **含** `conversation_id` |
| `tool_call_schema`(发给模型的) | **不含** ✓ |
| 直接用 `tool_call` 调用 | **`ValidationError: conversation_id Field required`** |

也就是说它对模型确实隐藏了字段,但**值必须另行注入**,而注入机制在 langchain-core 1.6.3 上没有现成文档。我没有去逆向它,而是换了**闭包工厂** —— `conversation_id` 根本不在签名里,模型既看不见也传不错,且不依赖任何未文档化的机制。已回写 spec §6.5(b),连带 §6.6 的注册表设计(因 `create_ticket` 需每请求构造,注册表不再是模块级常量)。

**教训**:`InjectedToolArg` 的 docstring 写着"are not included in the tool schema sent to language models"—— **它说的是"发给模型的 schema",不是"调用时的校验 schema"**。我按自己的理解把它当成了后者。文档没错,是我读得不够细。

**3. 又一个"想当然"被真机推翻:工具抛错时会发生什么。**

executor 的**整个设计**取决于"工具内部抛异常时,LangChain 是抛出还是包成 ToolMessage 返回"。我没猜,直接测了五种情况:

| 情况 | 实际行为 |
|---|---|
| 工具内抛 `RuntimeError` | **抛出** |
| 工具内抛 `SQLAlchemyError` | **抛出**(可区分) |
| 参数缺必填 | **抛出** `ValidationError`(可区分) |
| 参数类型不对 | **抛出** `ValidationError` |

全部**抛出**,`handle_tool_error` 默认 `False`。三类错误类型可区分 —— 这正好支撑 spec §6.7 的分类表。

**如果这里是"包成 ToolMessage 返回",整个错误分类就得推翻重写。**

**4. 一条我没敢下结论、专门去测的语义。**

「第二轮仍绑 tools 时模型会不会再调一次」—— 实测**没再调**。但我没有把这次观察写成设计:那是**模型行为,不是保证**。改成"第二轮不绑 tools"后,模型在结构上就没有能力再调。

plan 里为此专门写了一条断言 `test_second_round_uses_unbound_model`,并注明"谁把第二轮改成 `model_with_tools`,这条就挂"。

**5. 顺带验掉的一个低级坑**:`MAX_SESSIONS` 的淘汰如果用插入序而非 LRU 序,刚建的锁会被优先选中,破坏 `lock_for` 的幂等性 —— ch01 Task 4 已经在这上面栽过一次。plan 的 Task 8 因此明确要求 `lock_for` 里 `move_to_end`。
