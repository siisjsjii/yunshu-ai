**实测出来的七条(全部与文档不一致,已写进 spec §3.4 / §3.5 / §15.3)**

1. **`LangfuseSpan.update(**kwargs)` 的 kwargs 被静默丢弃** —— 源码 docstring 逐字
   `**kwargs: Additional keyword arguments (ignored)`。⇒ `root.update(**{"langfuse.trace.tags": …})`
   什么都不做、也不报错。**本仓「静默无效」家族第四次。**
2. **`LangfuseSpan` 上根本没有 `update_trace`**;模块级的 `langfuse.update_current_trace`
   也不存在(客户端上有的是 `score_current_trace` / `set_current_trace_io`)。
3. **`propagate_attributes` 中途 `__enter__` 有效**,但**只覆盖进入之后新建的观测**
   (实测:整段包裹 3 条;中途进入 2 条)。
4. **`_AgnosticContextManager` 没有 `__aenter__`** ⇒ 中途进入只能用同步 `__enter__`。
5. **`CallbackHandler.__init__` 只有 `(*, public_key=None, trace_context=None)`** ——
   文档里那套 `session_id=` / `tags=` 构造参数是 **JS SDK** 的。我照文档写出了 Python 代码,
   这是 §15.3 记的那处错。
6. **Metrics v2**:`query` 必须是**一个 JSON 字符串参数**;`sum_totalCost` **恒为 0**
   (模型没配价格)⇒ 统计只报 token;**按 `tags` 过滤的 `type` 必须是 `arrayOptions`**。
7. **Cloud 服务端会自己升级**:同一天早上是 4.41.0,下午再测是 **4.42.0**。

**翻车与返工**
- **又一次「验证装置自己产假绿」**:探针第一版里 `kwargs={}` 那两个分支**根本没把

  差点把"读回失败"当成"数据没落"。**两次都是同一个形状:输出看起来像结论,其实没测到。**
  修法:读回一律打 `resp.text`,不用异常字符串截断。

  所以不是网络不通)⇒ 探针与计划里的读回**一律带退避重试**。

**真机冒烟(spec §12.3-0 —— 全章唯一挡路的未知,已结清)**

前置踩了一次:Milvus 容器起不来(`panic: etcdserver: leader changed`)。**成因不是数据坏**,
是启动那一刻我正好在跑全量测试(24 核被占满),嵌入 etcd 的 `election-timeout: 1s` 没等到
ReadIndex 就变了 leader ⇒ SIGABRT。等机器空下来再 `docker start`,一次就起,**集合与 90 行
向量完好**。教训记一句:**这台机器上「Milvus 起不来」先看 CPU 忙不忙,别急着删数据。**

**结论 1:中间进入的 `propagate_attributes` 能穿透 LangGraph,给 graph 内部的 generation 打上 tag。**
判据(原始读回,`/api/public/v2/metrics` 按 `tags` 分组):

```
{"tags": ["ch09", "intent:商品咨询"], "sum_totalTokens": "1485", "count_count": "8"}
{"tags": [],                          "sum_totalTokens": "646",  "count_count": "8"}
```

- ① `intent:商品咨询` 那行**出现了**;② 它的 token 数 **1485 > 0**。
- **8 / 8 这个切法本身就是证据**:整条 trace 共 16 条观测,进入 tag 作用域**之前**的正好
  是 8 条(`LangGraph` 根 + `resolve_references` + 它的 generation + `classify_intent` +
  `RunnableSequence` + generation + `PydanticOutputParser` + `route_by_intent`),**之后**的
  也正好 8 条(`retrieve_knowledge` / `confidence_gate` / `_gate_route` / `agent` / agent 的
  generation / `route_after_agent` / `log_turn` / 手工 `retrieval`)。边界**恰好**落在
  `classify_intent` 上,与设计预期逐条对上。
- 第二个请求(订单意图)复现了同一件事:`intent:订单` 2207 tokens / 7 条。
  **顺带验到验收 5 的前提**:两行不同意图、token 不同,可分。⇒ **没走 spec §3.4 的退路。**

**结论 2(新发现,spec §3.3 的前提被实测推翻了一半):手工 span 落进了**另一条 trace**。**

按 `sessionId` 读回那次商品咨询请求的 16 条观测,**里面有 2 个 traceId**:

| 观测 | trace | parentObservationId |
|---|---|---|
| `LangGraph` 根及其下全部(含 `ChatOpenAI` generation、`TOOL 'query_order'`) | `879bf705…` | — |
| 手工 `retrieval`(RETRIEVER) | `6ff9033e…` | **null** |
| 手工 `tool:query_order`(TOOL) | `07ab51df…` | **null** |

成因:`start_as_current_observation` 的父级取自 **OTel 当前 span**,而 Langfuse 的
LangChain 回调**不把上下文挂成 current**(它用 LangChain 的 run tree 定父子)⇒
`graph.astream` 里根本没有"当前 span",手工 span 只好自己**开一条新 trace**
(带的 sessionId 与 tags 都对,但不在同一条 trace 上)。

连带推翻的还有 spec §3.3 表格的前提「工具执行一个 span 都不会自动出现」:
`spec.tool.ainvoke` **是** LangChain run,所以内置工具**已经**有一条嵌套得很好的
`TOOL 'query_order'` 在 `agent` 之下 —— 手工那条 `tool:*` 反而在别的 trace 上。
(手工 span 仍不是白开:它带 `ok` / `summary` / `error_kind`,那是 LangChain run 拿不到的。)

**没有修**:修法(把 `graph.astream` 再包一层 `observability.span("chat", as_type="span")`,
让 OTel 有 current span)会改**请求路径上的 trace 拓扑**,而 spec §3.2「挂点:一处」与
R5 的授权都只到「多传一个 `settings=`」为止。**已连同原始证据一并上报,由主控裁定。**
