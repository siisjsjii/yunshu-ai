## §1 目标与非目标

### 目标

1. **数据处理四步**:清洗(脱敏 + 格式)→ 归并术语表(17 类权威表)→ 分层抽样(80/10/10)→ 数据增强(只扩训练集)。
2. **标注**:多标签,口径是「一句话**字面提到**几个诉求就打几个标签,一个不多一个不少」;大模型照术语表预标 + 人工抽审。
3. **训练**:**哈工大讯飞 RoBERTa-wwm-ext 全参微调**(不用 LoRA),验证集盯分数 + 正则化 + 早停。
4. **评测**:留出测试集上按类目算精确率/召回率/F1 + 每类目矩阵;自动指标之外人工抽判错样本复核。
5. **部署**:导出成**推理服务**(独立进程),挂旁路**按批量**跑;结果写 `topic_classifications` 表(关联问题 / 多标签 / 归类时间)喂给后台看各主题分布。**实时对话主链路不调它。**
6. **前端**:飞轮后台加一个**主题分布页**,哪类堆得多一眼能看出来。
7. **A 支(用户 2026-09-25 追加)**:把「转人工」补成真正的**第九类意图** —— 走主力 agent,agent 调一个**模拟的**转人工接口。

### 非目标(明确不做)

- **LoRA / QLoRA**(那是大模型才用的手段)。本章是全参微调。
- **embedding 微调、意图识别微调**。(A 支改的是 ch06 的**路由表与提示词**,不是微调意图模型。)
- 接真人客服系统 —— 转人工仍是**模拟**。
- 不改 ch08 的工具系统 / 确认流 / MCP 接入。
- 跨会话长期记忆与用户画像(与 ch07/ch09 一致地不做)。
- `vectorize` / `mine` 那个**已知无死线的单槽**(ch09 已记账)本章**不修**,只是不去碰它。

## §2 设计依据(实测事实,不是推断)

> 本节的每一条都在本机亲跑过。**引用本文任何数字前先看它的来源。**

### 2.1 语料现状:合成不是「补足」,是**主力**

`.superpowers/probe_ch10_pool.py` 实测(2026-09-25):

| 源 | 原始行 | **去重后** |
|---|---|---|
| `low_confidence_questions`(飞轮池) | 63 | **31** |
| `messages` 里 `role='user'` | 861 | **154** |
| `review_queue` | 30(16 approved / 14 pending) | 30 |
| `evals/测试集.md`(人工写的) | 300 | 300 |

⚠️ **池子 63 行里只有 31 条不同的问题** —— 验收脚本反复问同一批题面留下的。真实去重语料合起来约 400 条;要做到 17 类每类几十条,得 **1200 量级**。所以需求里「池里量不够就让大模型造一批**补足**」这句话的分量要改写:**合成是主力**。

问题长度实测(`evals/测试集.md` 300 条):min 6 / 中位 **16** / 均值 16.3 / max **31** 字,`≥48` 字的 **0 条** ⇒ `max_length` 取 64 是宽裕上界(见 §7)。

环境:torch `2.11.0+cu128`(**CUDA 可用**)、transformers **`5.17.0`**、datasets `5.0.1`、accelerate `1.15.0`、sklearn `1.9.1`;`onnxruntime` / `optimum` **都没装**;HF 本地缓存**没有** RoBERTa-wwm-ext(首次要下,约 400MB)。

### 2.2 ⚠️ transformers **5.17.0** 的三处 v4→v5 差异(返工高发点,已逐条核对)

本机安装版源码 + 官方 `MIGRATION_GUIDE_V5.md`:

| v4 写法 | v5 正确写法 | 证据 |
|---|---|---|
| `Trainer(tokenizer=...)` | **`Trainer(processing_class=...)`** | `trainer.py` 的 `processing_class` 形参 |
| `TrainingArguments(evaluation_strategy=...)` | **`eval_strategy=...`** | `training_args.py:421` |
| `AutoTokenizer.from_pretrained(use_fast=...)` | **传了会被静默丢弃** | `tokenization_auto.py` 里 `kwargs.pop("use_fast", None)` |

最后一条尤其要注意:**它不报错,只是什么也没做**。

### 2.3 ⚠️ `problem_type` **不是配置项,是从 `labels.dtype` 猜出来的**

本机 `transformers/loss/loss_utils.py:94-118` 原文:

```python
if config.problem_type is None:
    if num_labels == 1:
        config.problem_type = "regression"
    elif num_labels > 1 and (labels.dtype in (torch.long, torch.int)):
        config.problem_type = "single_label_classification"   # softmax + CrossEntropy
    else:
        config.problem_type = "multi_label_classification"     # sigmoid + BCE
```

**后果**:标签若是**整数**张量(哪怕有 17 列),它会静默选**单标签**交叉熵;而且这个猜测**在第一个 batch 上定下来就锁死**。模型会被 softmax 推着**每句只报一个类** —— 而 **loss 照常下降、训练看起来完全正常**,验收 ③ 从原理上不可能过。

**此条属本仓「静默无效」家族**(前三个成员:ch06 未声明通道写入被丢弃、ch07 `add_messages` 给无 id 消息赋 uuid4、ch09 `response_format` 走 beta 路径)。

### 2.4 `optimum` 那条 ONNX 导出路**走不通**(用户已知情并选择绕开)

ONNX 导出功能今天在独立包 `optimum-onnx 0.1.0`,其 `Requires-Dist` 写死 `transformers<4.58.0,>=4.36`,而本机是 **5.17.0**。装它就要把 transformers 降到 4.57 —— 而 **BGE-M3 嵌入与 bge-reranker 都挂在 transformers 上**(FlagEmbedding 1.4.2),降级会牵动 ch03/ch04 整条检索链路,已标定的 `retrieval_score_threshold = 0.25` 与 `13/23` 那批读数**全部作废**。

**决定:不降级。** ONNX 本身仍可做(裸 `torch.onnx.export` + `onnxruntime 1.30.0`,后者与 transformers 版本无关),但用户已选 **transformers 服务**,此条只作为沿革记下。

### 2.5 A 支的沿革:「九类意图」是**需求变更**,不是本文读错代码

| 位置 | 原文 |
|---|---|
| `app/agent/routing.py:25-36` | `INTENT_TO_ROUTE` **正好 8 个键** |
| `app/prompts.py:279-292` | 「判断用户这一句话属于下面**八类**中的哪一类」 |
| `app/agent/state.py:133` | `intent: str  # 八类之一(含「其他」)` |
| ch06 spec §3.2 | 标题即「**意图八类** → 五出口」,表 8 行 |
| `evals/intent_cases.jsonl` | 期望标签只有那 8 个(物流4/订单4/商品咨询4/退款退货6/售后4/投诉4/闲聊3/其他9) |

**「五出口」是对的**:`app/agent/graph.py:64` 的 `_OUTLETS` 正好 5 个(`complaint_reply` / `chitchat_reply` / `fallback_reply` / `refund_offer` / `refund_explain`)。

**而「转人工」今天不是意图、也不是出口**:它是 `app/agent/nodes.py:94` 的 `CHOICE_HANDOFF`,只由**投诉出口**发一个 `choices` 帧,`app/static/index.html:1026` 接住后**纯前端模拟**(源码注释原文:「不接真人系统、不调后端」)。

⇒ 用户 2026-09-25 明确选择把它**补成真正的第九类**(§11),代价(改已上线路由 + 穷举单测 + 评估集 + 两处文档)已知情。

### 2.6 `JSON_TABLE` 实测可用(不是查文档推断的)

`.superpowers/probe_ch10_jsontable.py` 亲跑 MySQL **8.0.46**,返回 `[('尺码', 1), ('退换货', 1)]`。所以分布聚合在 SQL 里做,不用把标签拉回 Python 数。

### 2.7 ⚠️ 本章要防的**第二个**静默陷阱:标签顺序

模型输出的第 5 个 logit 对应哪个类目,**靠的是训练时标签列表的下标**。若推理服务自己硬编码一份类目顺序、而它与训练用的顺序不一致 —— 得到的是**一张完全错的分布图,而每一个组件都工作正常**:模型有输出、scores 在 0–1 之间、写库成功、页面画得出来。**没有任何东西会报错。** 防线见 §9.1。

### 3.3 两条不变量(「结构保证」,不靠自觉)

**① 实时对话主链路零调用分类器。** 用一条**源码扫描测试**守着 —— 照 ch09 那条「`app/` 下零处 import langfuse」的先例,断言 `app/agent/` 与 `app/api/chat.py` 下没有任何文件 import `topic_service` 或主题分类器。

**② 17 类表是唯一来源。** 预标 prompt、合成配额、训练标签顺序、评测类目、分布页图例,**全部 import 同一个 `app/topic/taxonomy.py`**。任何一处硬编码类目名就是漂移的开始 —— 本仓已有先例(`retrieval_score_threshold` 改一处漏一处)。

### 3.4 交付物与可复现性

权重放 `models/topic-clf/` 并 **gitignore**(400MB 二进制不入 git,与 `evals/results/`、BGE-M3 权重同规矩)。

**可复现性靠「脚本 + 冻结的测试集」,不靠权重入库** —— 新 clone 跑一遍训练脚本(约十几分钟)就有等价产物;而**测试集冻结进 git**,所以不同机器上跑出来的 F1 是**同一个东西上**的读数。

### 4.2 ⚠️ 这张表里**没有**「投诉」「闲聊」「转人工」—— 这是刻意的,不是漏了

它们都是**意图**(用户想干什么),不是**主题**(问题关于什么)。所以:

- 「我要投诉」→ 主题是 **`其他`**;
- 「你好呀」→ **`其他`**;
- 「我要转人工」→ **`其他`**。

**必须写进表里**,否则下一个人会以为 9→17 映射表漏了三行。两个词表的**定位差异**是设计的一部分。

### 4.3 9→17 映射(是**有损投影**,不是等价变换)

`app/topic/taxonomy.py`:

```python
INTENT_TO_TOPICS: dict[str, tuple[str, ...]] = {
    "物流":     ("物流",),
    "订单":     ("订单修改",),
    "商品咨询": ("商品信息",),
    "退款退货": ("退换货",),
    "售后":     ("保修维修", "质量问题"),   # ← ch06 的「售后」把修与坏揉成一个,这里拆开
    "投诉":     ("其他",),
    "闲聊":     ("其他",),
    OTHER:     ("其他",),
    "转人工":   ("其他",),                # ← §11 新增的第九类
}
```

**两条必须写明的性质:**

1. **它是有损的。** 9 个意图投影到 17 个主题会丢信息(投诉/闲聊/转人工 → 其他),而一个意图可能散到多个主题(售后 → 保修维修 / 质量问题)。**它是「投影」,不是「等价变换」**;别期待 `逆向(正向(x)) == x`。
2. **谁改了意图集,谁就要改这张表。** 加一条**测试**:断言 `INTENT_LABELS` 的**每一个标签**都在 `INTENT_TO_TOPICS` 里有条目。这条测试的价值在 §11 会兑现 —— 加第九类时它会**响亮地失败**,而不是静默少一行。

## §5 数据处理四步

全部落在 `scripts/prepare_topic_data.py` + `app/topic/`(纯函数)。**中间产物落盘、可单步重跑**(照 `build_kb.py`「重跑 = 幂等补齐」的先例;网络断在一半不用从头来)。

### 5.1 第 1 步 清洗(`app/topic/clean.py`)

- **脱敏**:手机号 → `<手机号>`、订单号 → `<订单号>`、邮箱/身份证同理。理由:防模型学伪特征(「带长数字的就是订单类」),顺带把真实用户数据从语料里去掉。
- **格式**:全角→半角、合并连续空白、去首尾、去重复标点。

**⚠️「修错别字」这一项被拿掉了(用户 2026-09-25 批准的设计变更)。**

需求原文是「清洗:脱敏、**修错别字**和格式」。实际做法改为「**保留错别字 + 在增强阶段主动注入**」。三条理由:

1. **改干净 = 制造训练/部署不一致。** 部署时用户就是会写错别字(语料本来就来自他们);训练语料被修干净后,模型见到的文本比真实的好。**最坏的不是掉分,是测不出来** —— 测试集也是修过的 ⇒ F1 虚高,而这个下降在指标上不可见。
2. **修正本身会引入幻觉,而且没有任何东西会发现。** 「起球」→「气球」这种错改,污染的是**全部**数据,静默无声。
3. **这件事应该反过来做**:增强阶段主动注入(同音/形近/多字漏字),它只扩训练集、不动测试集,方向是对的。

**⚠️ 无论改不改都要立的规矩:清洗函数训练侧与推理侧同源。** `prepare_topic_data.py` 与 `classify_topics.py` **import 同一个 `clean.py`**。否则就是经典的 train/serve skew:训练时洗、推理时不洗(或反过来),模型在真机上看到的是另一种文本。**写成测试守着。**

### 5.2 第 2 步 归并术语表(`app/topic/taxonomy.py`)

「归并」= 把口语说法归到标准类目上(**不是删同义词,是建立映射**)。产物 `evals/topic/taxonomy_review.csv` **先给用户过目**——后面所有预标、合成、裁决都照它走,**它歪了整章数据都歪**。

### 5.3 第 3 步 分层抽样(80/10/10)

总量约 1200 ⇒ 训练 ~960 / 验证 ~120 / 测试 ~120。

- **抽样对象是「合并后的 1200 条」,不是真实与合成各抽一遍** —— 否则两份的 80/10/10 拼起来才是整体的 80/10/10,而真实那 400 条只出 40 条测试样本,§8.4 的「真实 80」那一列就凑不出来。
- 按**主标签**分层抽样,**并施加两条约束**:
  1. **测试集的构成必须正好是「真实 80 + 合成 40」**(§5.5 双池分离),这是分层抽样要满足的硬条件,不是抽样完再看结果;
  2. **常见标签组合在三份里都要出现** —— 否则测试集里可能一条多标签都没有,验收 ③ 就无从谈起。
- **测试集规模问题必须当面记账**:120 条 ÷ 17 类 ≈ **每类 7 条**,一条判错掉 0.14,**那个数字不能当结论引用**。所以:**头四类(退换货/物流/尺码/发票)每类保证 ≥15 条**,其余类按比例,总数仍 120。这样「四大类领头」在测试集上是**真的**,而不是术语表里的一句场面话。

### 5.4 第 4 步 数据增强(**只扩训练集**)

同义词替换 + 句式微调,大模型做。**增强只作用于训练集**(真实的与合成的**都**扩),**验证集与测试集一条都不动** —— 扩了测试集,§8 那套指标就不再有意义。

**两条硬约束:**

- **增强后标签必须逐条重验,变了就整条丢。** 「买大了想退」改成「买多了想退」标签不变;改成「不喜欢这个想退」,标签就从 `尺码+退换货` 变成 `退换货` —— 这是**静默的标签漂移**,而它看起来只是一次正常增强。
- 增强 prompt **逐条带原标签 + 边界说明**,明确要求「保持诉求个数与类别不变」。
- 顺带**注入错别字**(同音/形近/多字漏字)—— 见 §5.1 第 3 条。

### 5.5 方案 A:配额造 + 形态强制 + 双池分离(用户批准的语料方案)

**合成不是「再来一批问题」,而是按配额、按形态造:**

- **配额**:17 类每类约 45 条,`退换货/物流/尺码/发票` 四个头类加倍;`其他` 类**要留配额**(语料里它不会少,而合成时最容易忘)。
- **形态强制**(本方案的全部价值所在):
  - **≥30% 多标签**(2–3 个诉求)—— 否则模型退化成「只报最显眼的那个类」,验收 ③ 直接挂;
  - **≥15% 近邻边界对** —— 保修维修 vs 退换货、运费 vs 物流、价保 vs 优惠活动,**每对必须成对出现且数量相当**;
  - **禁止出现类目名与边界说明的原词**(不许造出「保修维修怎么办」这种句子)。不设这条,模型学到的就是**关键词匹配**,F1 会很漂亮而真机一用就废。
- **双池分离**:训练/验证 = 合成 + 真实混;**测试集 = 真实 80 + 合成里抽 40,100% 人工过**。

### 5.6 三源合流

池子 31 + 真实对话 154 + `evals/测试集.md` 300,去掉重叠后约 400 条真实语料,**合成补到 1200**。

## §6 标注

### 6.1 口径:这是「**字面**」口径,不是「意图」口径

判据是**原文里有没有那几个字**,不是「用户真正想要什么」。把口径钉死的例子(直接进术语表正反例):

| 原话 | 标签 | 为什么 |
|---|---|---|
| 买大了想退 | `尺码` + `退换货` | 字面两个诉求 |
| 退货运费谁承担 | `退换货` + `运费` | 「退」归退换货,「运费」单独命中 |
| 保修期内坏了能退吗 | `保修维修` + `退换货` | 修归保修维修、退归退换货 |
| 满多少钱包邮 | `运费` | 「包邮」是运费概念,不是券/满减,不给 `优惠活动` |
| 我要转人工 | `其他` | 不是主题,是诉求;17 类里没有它 |

### 6.2 ★ 预标必须带「证据串」—— 这是「字面提到」的**结构性保证**

预标 prompt 要求模型**对每个标签给出「来自原文的哪几个字」**,然后**机械校验:证据必须是原文的子串**。不是子串 ⇒ 该条判为「待人工」。

**不做这一步,「字面提到」就只是 prompt 里的一句话,没有任何东西在守它** —— 模型可以凭语义联想打标签,而你从输出上看不出来。有了证据串,它变成一个**可自动检验**的条件。顺带两个好处:证据串能进 `topic_classifications` 让结果可解释,也能进分布页的悬停提示。

预标走本仓既有的 `app/llm.py`,**必须用 `json_mode`**(本仓硬约束:该端点上 `function_calling` 与 `json_schema` 都返回 400)。连带:提示词里**必须出现字面 `JSON` 字样**,且 `ChatPromptTemplate` 按 f-string 解析,**不得有裸花括号**。

### 6.3 ★ 人工抽审 = **测错误率**,不是逐条改

训练/验证集**按类分层各抽 5 条**(17×5 = 85 条)。目的是**估一个错误率**:

- 错误率 **> 10%** ⇒ **不训练**,先修 prompt 重标;
- **≤ 10%** ⇒ 接受,并**把这个错误率写进报告**。

⚠️ **训练集标签的错误率,是本章 F1 的已知上界。** 训练标签有 5% 是错的,模型的天花板就低于 100% —— 这句话必须和 F1 **并排**出现在报告里,否则那个数会被读成「模型的能力」。而逐条改 85 条制造的是「已经审过了」的**错觉**:它只覆盖 9%,剩下 875 条没人看。

### 6.4 测试集 100% 人工裁决

它是对外报数的**唯一**依据。走 **CSV**(`evals/topic/labels/*.csv`),列:

```
id, 问题, 预标标签, 判定(ok/改), 最终标签, 备注
```

### 6.5 两条直译需求原话的指标

- **标签个数完全一致率** —— 预测个数 == 真实个数;
- **整条完全一致率(subset accuracy)** —— 标签集合完全相同(最严、最诚实)。

不用 macro-F1 含糊过去。

### 6.6 产物格式(`evals/topic/labeled.jsonl`,append-only、可断点续跑)

```json
{"id": "s-0001", "question": "买大了想退", "labels": ["尺码", "退换货"],
 "evidence": {"尺码": "买大了", "退换货": "想退"},
 "provenance": "synthetic", "source": "gen", "split": "train"}
```

## §7 训练

**基座** `hfl/chinese-roberta-wwm-ext`(约 400MB,首次下载),`AutoModelForSequenceClassification`,`num_labels=17`。

### 7.1 ★ 三道防线对付 §2.3 那个静默陷阱

1. `from_pretrained(..., problem_type="multi_label_classification")` —— **显式传,不靠猜**;
2. collator / 数据集里**断言标签是 float**;
3. 一条**单测**:「5 个标签的样本,loss == 手算 `BCEWithLogitsLoss`」,**不是** CE。

### 7.2 v5 API 名字(见 §2.2)

`Trainer(processing_class=tokenizer, ...)`;`TrainingArguments(eval_strategy=...)`。

### 7.3 超参(按实测的语料性质定,不是抄默认值)

| 项 | 取值 | 依据 |
|---|---|---|
| `max_length` | **64** | §2.1 实测:问题中位 16 字 / 最长 31 字 / `≥48` 字 0 条 |
| `learning_rate` | `2e-5` | BERT-base 全参微调的常规量级 |
| `weight_decay` / `warmup_ratio` / dropout | `0.01` / `0.1` / `0.1`(RoBERTa 自带) | 用户点名的「正则化」落在这一行 |
| `per_device_train_batch_size` | 32 | 句子短,显存不是瓶颈 |
| `num_train_epochs` | 15 | 配合早停 |
| `EarlyStoppingCallback` | `patience=3, threshold=0.001` | 用户点名的「早停」 |

> ⚠️ **HF 硬约束(先说以免返工)**:`load_best_model_at_end=True` 时 **`save_strategy` 必须等于 `eval_strategy`**,否则直接抛错。

### 7.4 ★ 早停盯 **micro-F1**,不盯 macro-F1

验证集 120 条 ÷ 17 类 ⇒ **每类 7 条**。macro-F1 在这个样本量下抖动极大,拿它早停等于**让噪声决定什么时候停**。所以 `metric_for_best_model` 取 **micro-F1(样本级)**;macro-F1 照常算、照常报告,但**不参与决策**。

### 7.5 ★ 不用 `pos_weight`

`BCEWithLogitsLoss()` 保持默认。加了 `pos_weight` 会**改掉概率尺度**,阈值语义(0.5)与分布页上显示的置信度就都不再是「概率」。类别不平衡交给 **§5.5 的配额造数据**在源头解决。

「全参微调」这条也让正则化不是装饰 —— 102M 参数喂 ~960 条样本会很快过拟合,早停是必需品。

### 7.6 ★ 阈值

sigmoid + **全局单阈值 0.5** 作基线;验证集上做一次 **0.3–0.7 扫描**,把表打进报告。**不做每类阈值** —— 在每类 7 条上调每类阈值,调的是噪声。

### 7.7 产物

`models/topic-clf/`(**gitignore**):权重 / `config.json` / tokenizer / **`train_meta.json`**。

`train_meta.json` 必须有:**数据指纹**(训练集内容 hash)+ 种子 + 超参 + 最终 val 指标 —— 否则「这个权重是哪份数据训的」永远说不清,而语料是会被重造的。

## §8 评测

### 8.1 指标(全部在冻结的测试集上跑)

| 指标 | 对应需求的哪句话 |
|---|---|
| **每类 P / R / F1 + support**(17 行表) | 「按类目算精确率、召回率、F1」 |
| **micro-F1 / macro-F1** | 两个都给,并说明差别 |
| **整条完全一致率(subset accuracy)** | 「一个不多一个不少」的最严读法 |
| **标签个数完全一致率** | 「一个不多一个不少」的字面读法 |

### 8.2 ★「混淆矩阵」拆成两张,并且第 2 张**不叫**混淆矩阵

单标签的混淆矩阵是「真实类 × 预测类」;多标签**没有唯一的预测类**,直接画 17×17 会得到一张人人能画、谁也读不懂的图。所以:

1. **每类一张 2×2**(TP / FP / FN / TN)—— 17 张小表,是每类 P/R/F1 的**来源**,读数对得上;
2. **一张 17×17 的「误判流向矩阵」** —— 行 = 真实标签,列 = 预测标签,格 = 「本该是 i、却被判成 j」的次数。**一眼看出哪两类最容易混**(`运费↔物流`、`退换货↔保修维修`)—— 那正是 §4.1 三条边界的**验收集**。

⚠️ 名字特意不叫「混淆矩阵」:本仓吃过名字与语义不符的亏(`agent_steps` 读作「步数」,实际是绑工具轮次的序号)。报告里要写明它与经典混淆矩阵的区别。

### 8.3 ★ 小样本类的 F1 不许当结论引用

每类打 support,**support < 15 的类那一行标 `†`**,表头写一行「† 样本数不足,该行 F1 不成结论」。这防的正是「拿一张 17 行的漂亮表格,读出 17 个结论」。

### 8.4 ★ 分层报告:同一套指标打三遍

合成语料即便人工核过,它**与训练集同源**,同源样本上的表现天然偏高。所以三列并排:

| | 全体 120 | **只看真实 80** | **只看合成 40** |
|---|---|---|---|
| micro-F1 | | | |
| subset accuracy | | | |

**「只看真实 80」那一列才是这个模型在真机上的预期表现。**

### 8.5 ★ 人工抽判错样本判的是「**谁错了**」

自动指标跑完,把**判错的样本**导成 CSV(原话 / 真实标签 / 预测标签 / 预标的证据串),用户判:

- **模型错**(标签对、模型没学到位)→ 归到模型的账上;
- **标签错**(模型对、预标标错)→ **归到数据的账上**。

**这个区分是本次复核的全部价值**:如果判错里多数是标签错,那 F1 低**不是模型的问题**,要修的是数据不是训练 —— 而只看一个 F1 数字永远分不出来。导出**最多 60 条**。

### 8.6 产物与可复现

`evals/topic/report.md`(给人读)+ `report.json`(机器可读、可 diff)+ 两张矩阵的 CSV。`eval_topic_clf.py` 一条命令产出 —— **这是验收 ① 的落点**。

评测脚本只读冻结的 `topic_test.jsonl` + 一个 checkpoint 路径,**不参与任何随机**。同一份权重跑两次,报告逐字节相同。

### 11.2 ★ 提示词里必须钉死的一条边界:**投诉 ≠ 转人工**

- 「你们客服太差了,我要投诉」→ **投诉**(投诉出口**会给出**转人工按钮,但它自己不是转人工请求);
- 「我要转人工」「找真人客服」→ **转人工**。

不加样例,模型会把它们揉成一个 —— 而揉成一个的后果是**投诉出口被绕过**,那段安抚话术 + 工单选项就永远不出现了。

### 11.3 ★ 用户点名要的走法:**走主力 agent**

用户原话:「转人工也是一个,**走主力 agent**,主力 agent 调一个转人工的接口(模拟)」。因此:

- 路由值是新的 `HANDOFF`,目标是**已有的 `agent` 节点**(不是新出口);
- **转人工算只读、直调不确认**(用户 2026-09-25 拍板)⇒ `policy.py` 里**显式声明**,并配一条测试断言 `kind_of("transfer_to_human") == "read"`。
  ⚠️ 把这条测试的**判别力**说清楚:因为「未声明 = 只读」,**它今天对一个漏声明的实现同样会通过** —— 它守的不是「有没有声明」,而是「**将来有人把它改成 write** 时会被拦下来」。理由写进代码注释:它是模拟接口、无真实副作用,且要求用户对「转人工」再点一次确认是坏体验。

### 11.4 ★ 结构风险落成一个**可测的数**

转人工走 agent 意味着**它发生不发生,取决于模型记不记得调工具** —— 结构上拦不住(`routing.py` 的立身之本是「模型只决定意图标签,不决定走向」,这是本章唯一一处例外,**已当面告知用户,用户知情选择**)。

但**可以测出来**:

- 评估集里加 **5–8 条**转人工用例,断言**端到端回复里出现了工号/等待时长**,而**不是只断言意图标签对**。只断标签的话,「分类对了但模型没调工具、用户什么也没得到」会**全绿通过**;
- 模型偶尔不调工具的比例,**是写进报告的一个数**,不是「已交付」。

> 本仓先例:ch08 的「缺必填项追问」当时**没测也测不出**,交付时只能写「未达成」(见 CLAUDE.md)。这次至少把它变成一个读数。

### 11.5 不做

不接真人系统(仍模拟)、不开新出口、不动五出口、**不动任何既有意图的行为**。

## §15 实现订正

> 实现期与本节冲突之处一律记在这里,**不改上面的历史章节**。格式照 ch03–ch09 的惯例:
> 每条写「原设计 → 实际 → 为什么 → 代价」。

### 15.1 订正:§4.1 的**边界说明**有三行在代码里不是逐字原文(措辞 + 把规则折进行内)

- **原设计**:§4.1 那张表的「边界说明」列是权威文本;表前的引言另起一句给出用户点名的
  三条近邻边界(「**修归保修维修、退归退换货;运费管钱、物流管货;价保是补差价、
  优惠活动是券和满减**」)。任务 1 的 brief 要求「`BOUNDARY` 逐条照抄 §4.1」。
- **实际是**(T1 落地,2026-09-26):`app/topic/taxonomy.py` 的 `BOUNDARY` 有三行与
  §4.1 的**字面**不同 ——
  | 行 | §4.1 的字面 | 代码 / CSV 里的字面 |
  |---|---|---|
  | 退换货 | 或**问**退换货的规则与流程 | 或**询问**退换货的规则与流程 |
  | 物流 | (引言另起一句「运费管钱、物流管货」) | 句尾补 `(管**货**)` |
  | 运费 | (同上) | 句尾补 `(管**钱**)` |
- **为什么会差**:两处都是**有意**的,不是抄错。① brief 自己的代码块写的就是改过的文本
  (「询问」),实现者照代码块落地 —— 那是对的,因为 brief 的代码块是 brief 的**正文**,而
  「照抄 §4.1」是 brief 的一句注释,**两者冲突时以正文为准**。② 行 2 / 6 的括号是把 §4.1
  **引言里那条用户给定的规则折进它所管辖的那两行** —— 边界说明是逐行进 prompt 的
  (`render_taxonomy_for_prompt`),规则只写在引言里就**不会随行进 prompt**,
  而「运费管钱、物流管货」正是这两行存在的全部理由。
- **代价**:§4.1 的**字面**与代码 / CSV 之间不再逐字相同 ⇒ **凡拿 CSV 去对 §4.1 原文的人
  必须先读这一条**,否则会把这三行读成抄写错误。这是本仓「文档即设计源」这条规矩的一次
  真实磨损,记在这里而不是把代码改回去,是因为**折进行内确实更好**(规则跟着它管辖的行走)。
- **证据**:`evals/topic/taxonomy_review.csv` 第 1 / 2 / 6 行(用户已签字);
  `app/topic/taxonomy.py` 的 `BOUNDARY`;`tests/test_topic_taxonomy.py` 的
  `test_every_label_has_a_boundary_sentence`(只断「有边界说明」,**不断措辞** ——
  措辞的看守是 §4.1 与这条订正的对照,不是测试)。
