================= 六条行为(真 fetch → 真服务端)=================

① 没 token 时 authBoot:应弹浮层、且 onReady 不该被调用
  ok  #auth-overlay 显示出来了(style.display="flex")
  ok  onReady **没有**被调用(没 token 就不 boot —— 这条就是「不往下走」)

② 密码错:浮层要显示服务端那句 detail,且 token 不许落库
  服务端原文 = "用户名或密码不正确"
  ok  浮层上是服务端那句(读到 "用户名或密码不正确")
  ok  localStorage 里没有 token
  ok  浮层还开着(登录没成功,用户还有机会再试)

③ 密码对:token 要落 localStorage、浮层收起、onReady 这才被调用
  ok  localStorage["mewhelp.jwt"] 是一个 JWT(三段点分,长度 168)
  ok  浮层收起了(style.display="none")
  ok  onReady 被调用了 —— 登录成功是**唯一**放行「往下走」的闸

④ authFetch:401 之后要**重放原来那次调用**(这是整件事的承重点)
  ok  第一次请求 401 之后浮层弹出来了
  ok  第一次那条**没带** Authorization(它就是这么 401 的)
  ok  这次调用**还挂着** —— 在等用户登录(没有自己放弃)
  ok  登录之后那次调用回来了
  ok  一共发了 2 次(1 次 401 + 1 次重放)
  ok  重放那次带上了**新拿到**的 token
  ok  重放收回来的状态码 = 200
  ok  重放拿到的 body 是真数据(demo-user 名下 581 条会话)

⑤ 垃圾 token:下一次受保护请求要 401、浮层要再弹,且**不许自己重放**
  ok  带着垃圾 token 的请求把浮层又弹出来了
  ok  此刻只发了 1 次 —— 没有「登录→401→再弹」的自转
  ok  那一次确实是拿着垃圾 token 发的
  ok  401 之后 token 被清掉了(垃圾 token 不会留在手里)
  ok  重新登录之后这次调用也回来了
  ok  重放收回来的状态码 = 200

⑥ stream:true:流式那次 401 只弹浮层,**绝不重放**(重放=替用户再发一条消息)
  ok  这次调用**当场就回来了**(没有挂在登录上)
  ok  交回调用方的就是那个 401(status=401)
  ok  body 是服务端的 401 文案("{\"detail\":\"未认证\"}")
  ok  浮层还是弹了(用户被明确告知要登录,而不是静默失败)
  ok  登录之后 /api/chat/stream 仍然只被打了 1 次

⑦(附加)两个页面引的 auth.js 路径,在真服务端上取得到、且与磁盘上逐字节相同
  ok  index.html 引的是 /auth.js ⇒ HTTP 200,内容与磁盘逐字节相同
  ok  admin.html 引的是 /auth.js ⇒ HTTP 200,内容与磁盘逐字节相同

⑧ 并发 401:4 轮 × 3 个并发,**每一个**都要回来(修前读数 = 1/3)
  第 1 轮:回来了 3/3,其中重放成功(200)的 3 个
  第 2 轮:回来了 3/3,其中重放成功(200)的 3 个
  第 3 轮:回来了 3/3,其中重放成功(200)的 3 个
  第 4 轮:回来了 3/3,其中重放成功(200)的 3 个
  ok  4 轮**全部**是 3/3 —— 不是某一轮碰巧(修前是 1/3)

⑨(附加)顶栏徽标 + 退出:要读到登录的那个人,点退出要清 token 并重载
  ok  顶栏被填成了三个节点(用户名 / 分隔符 / 退出)
  ok  用户名与角色来自 /api/auth/me(排面 "demo-user(admin)",服务端说 "demo-user(admin)")
  ok  第三个节点是「退出」
  ok  点「退出」之后 token 被清掉了
  ok  而且触发了一次 location.reload(1 次)—— 重载之后 authBoot 才会重新弹浮层
